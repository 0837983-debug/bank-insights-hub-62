## 1. Что это за проект

**Bank Insights Hub** — full-stack веб-приложение для аналитики банковских финансовых
показателей. Представляет собой динамический дашборд, который:

- отображает **KPI-карточки** (капитал, ROA/ROE, ЧПД, операционная прибыль и т.д.)
  и **иерархические таблицы** (Баланс, Финансовые результаты);
- загружает данные из файлов **XLSX/CSV** и прогоняет их через конвейер
  `STG → ODS → MART`;
- строит структуру интерфейса **динамически из базы данных** (конфигурация хранится
  в БД, а не в коде).

Стек: **Frontend** — React 18 + TypeScript + Vite 5 + Tailwind + shadcn/ui (Radix) +
TanStack Query v5; **Backend** — Node + Express 4 + TypeScript + PostgreSQL (`pg`,
без ORM) + SQL Builder; **Docs** — VitePress.

### 2.2. Найденные недостатки

#### Критические (безопасность)

1. **Захардкоженный пароль боевой БД в коде.**
   Файл `backend/src/config/database.ts` содержит пароль и адрес AWS RDS как значения
   по умолчанию. Секрет закоммичен в репозиторий. **Требуется срочная ротация и вынос
   всех секретов в переменные окружения (.env).**
2. **Отсутствие аутентификации и авторизации.** Все endpoint'ы полностью открыты,
   ролей нет, `Auth.tsx` заархивирован. Приложение «голое» — любой пользователь имеет
   доступ ко всему. Для банковских данных это недопустимо.
3. **Тесты бэкенда подключаются к реальной БД.** Файл `queryLoader.test.ts`
   реально выполняет `pool.connect()`, а дефолтные настройки указывают на боевой
   AWS RDS. Запуск тестов без локальной БД может обратиться в прод.

#### Высокие

4. **Единая точка `/api/data` + генерация SQL из конфига в БД.** Подход гибкий,
   но плохо масштабируется и расширяет поверхность атаки (инъекции, отсутствие
   типизированных контрактов, сложность кэширования/аудита). Требуется аудит
   безопасности и, вероятно, рефакторинг контрактов.
5. **Конфигурация дашборда не редактируется через интерфейс.** Все настройки
   (`config.*`) меняются только через SQL-миграции. UI-редактор (`ConfigEditor.tsx`)
   существовал, но был заархивирован. Это главный источник неудобства.
6. **«Тестовая консоль» (DevTools) встроена в обычный фронтенд.** Страница
   `/dev-tools` даёт доступ к генерации и просмотру SQL, хардкодит `localhost:3001`.
   Не должна быть доступна конечным пользователям (менеджерам).
7. **CORS и URL захардкожены под localhost.** В `server.ts` прописаны только
   локальные origin'ы; `DevTools.tsx` — `localhost`. На внешнем сервере приложение
   работать не будет без выноса в переменные окружения.

#### Средние

8. **Массовое использование миграций для правки конфигурации UI.** 79+ миграций,
   часть из которых — «показать/скрыть колонку», а не структурные изменения. Это
   противоречит лучшим практикам: миграции должны применяться для существенных
   изменений схемы, а не для показа колонок. Приводит к сотням миграций и сложному
   развёртыванию цепочкой.
9. **Документация частично устарела.** `backend/README.md` описывает удалённые
   endpoint'ы (`/api/kpis`, `/api/table-data`, `/api/layout`). Отдельные страницы
   `docs/` также расходятся с кодом. Ориентироваться стоит только на `docs/context/*`
   и сам код.
10. **Нет глобального управления состоянием на фронтенде.** Используются
    `useState`/`useMemo` + TanStack Query. Приложение страдает от **props drilling**
    (данные передаются через несколько уровней компонентов). Контекст используется
    только внутри внутренних shadcn-компонентов.
11. **TypeScript не в strict-режиме.** В `tsconfig.app.json` — `"strict": false`,
    `"noImplicitAny": false`, `"noUnusedLocals": false`. Требуется ужесточение.
12. **ESLint не строгий.** Многие правила отключены (`no-console`,
    `security/detect-object-injection`, `sonarjs/cognitive-complexity`,
    `no-explicit-any` — только warn). Требуется усиление.
13. **Сервисы не изолированы / нет DI.** Зависимости импортируются «изнутри»
    (напрямую `pool`), тесты не могут заменить их моками. Не соблюдаются в должной
    мере принципы SOLID, чистых функций и инверсии зависимостей.
14. **Устаревший стек.** React 18 (актуально 19.2.x), Vite 5 (актуально 6/7).
    Библиотека для графиков — recharts (можно расширить). Депенденсы стоит
    обновить осознанно.
15. **Docker Hub: накопление образов.** Workflow публикует `:latest` и `:<sha>`.
    `:latest` перезаписывается, а `:<sha>` накапливаются. Нужна политика очистки.

#### Детализация задачи 1.4 — админ-панель управления аккаунтами (super_admin)

- **Страница управления аккаунтами** доступна только супер-админу.
- **Создание пользователей:** супер-админ создаёт аккаунт и назначает роль
  (менеджер / просмотр). Создание через UI возможно только для **не-супер-админских**
  ролей — защита от эскалации привилегий (нельзя создать второго супер-админа
  через интерфейс).
- **Назначение/смена роли** для существующих пользователей.
- **Блокировка / разблокировка** любого пользователя (поле `is_active`) — заблокированный
  пользователь не может войти и получать данные.
- **Удаление** учётной записи.
- **Управление паролями (политика однократного показа):**
  - при создании пользователя система **генерирует сложный пароль** и показывает его
    **один раз** (админ должен передать его пользователю);
  - после закрытия экрана пароль больше **не отображается**;
  - сброс пароля = генерация нового сложного пароля с **однократным показом**.
  - Хранение — только bcrypt-хеш, сам пароль в БД/логах не хранится.

## 5. Принципы разработки (целевые)

- **ACID** — транзакционность обеспечивает PostgreSQL; конвейер загрузки должен
  использовать транзакции и откат (уже частично реализовано).
- **SOLID** — единая ответственность, открытость/закрытость, подстановка,
  разделение интерфейсов, инверсия зависимостей.
- **Чистые функции** — функции ничего не знают об окружении, принимают всё через
  аргументы, детерминированы и легко тестируются.
- **DI/инверсия зависимостей** — сервисы получают зависимости (репозитории, логгер,
  конфиг) через конструкторы; в тестах заменяются моками.
- **Изоляция сервисов** — каждый сервис самодостаточен и не зависит от других.
- **Безопасность по умолчанию** — секреты в env, авторизация, валидация, без инъекций.

## 6. Приложение

### 6.1. Docker (кроссплатформенность)

Контейнеризация сделана для единообразного запуска на Windows/macOS/Linux
(заказчик указал, что без Docker система не работала на macOS). Подтверждено:

- `backend/Dockerfile` — node:20-alpine (build) → runner;
- `frontend/Dockerfile` — node:20-alpine build → nginx:alpine;
- `docker-compose.dev.yml` / `.prod.yml` + bootstrap-скрипты.

Профили: `local-postgres` (встроенная БД) и `external-db` (внешняя БД/RDS). Docker
**не обязателен** — можно запускать локально с собственным PostgreSQL.

### 6.2. Docker Hub

- Репозитории `ayreon208/*` — по умолчанию публичные (проверяется на hub.docker.com
  без логина).
- На аккаунте `ayreon208` есть также сторонние учебные проекты (`foodgram`,
  `kittygram`, `taski`) — к банковскому проекту отношения не имеют.
- Публикация банковских образов: `docker-publish.yml` → `:latest` + `:<sha>`.
  Требуется политика очистки старых тегов.

### 6.3. Тестовые данные

Готовые наборы для проверки системы лежат в `test-data/uploads/` (валидные CSV
баланса/финреза и намеренно битые файлы для проверки валидации). Также есть E2E-тесты
в `e2e/`.
